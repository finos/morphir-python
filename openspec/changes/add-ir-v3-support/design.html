Context

See proposal.md for motivation. Today packages/morphir/src/morphir/ir/ holds a v4-shaped model: Library, Specs, and Application distributions; PackageInfo(name, version: str); ValueAttributes(source, inferred_type, extensions); TypeAttributes(source, constraints, extensions); and Hole, Native, and External as value nodes. morphir/ir/json.py is a placeholder encoder with a generic dataclass fallback and no decoder, so the repo cannot read any IR JSON yet.

morphir-elm pins currentFormatVersion = 3. Its decoder reads formatVersion with Decode.int, accepts 3 and 1 (through CodecV1), and rejects everything else, including 2 and any string. Upstream, finos/morphir has since published a format-version contract with string releases, a support table, and stable diagnostic codes, and has minted IR 3.1.0, which adds a v3 Specs distribution and v3 document trees. IR v4 is still being stabilized and its sources disagree with each other.

Goals and non-goals

Goals: first-class v3 (format 3.0.0) and v4 Python IR; morphir-elm-compatible format-3 JSON; a draft v4 JSON codec; permissive format-version reading with upstream diagnostic codes; v3→v4 forward migration; v4→v3 reverse migration with structured failures; a Typer CLI for inspect and convert.

Non-goals: IR formats 1 and 2; IR 3.1.0 (v3 Specs and v3 document trees); v4 document trees and YAML; realigning the Python v4 model with every upstream v4 decision; Morphir Compatibility Kit adapter integration; changing morphir-elm or finos/morphir; silent data loss on downgrade.

Author calls

Confirmed by the change author (2026-10-27). These are not agent defaults.

  • Separate capability ir/format-version. Keep version recognition, normalization, support-table checks, and diagnostics in their own capability and package surface (morphir.ir.format_version), shared by the v3 codec, the draft v4 codec, and the CLI. Do not fold that contract into ir/v3 alone.
  • Separate task group and bead for the draft v4 JSON codec (morphir-ukvn.8.11). Land draft v4 encode/decode as its own sequenced work item between v4 package layout and migrations, so the draft interchange gap stays visible and pin-able. Do not bury it inside the layout or migrate groups.

Decisions

FV-1. Permissive format-version reading, canonical writing

A shared reader in morphir.ir.format_version accepts a JSON integer N, a string "N", and a string "N.minor.patch", and normalizes each to an exact release. Component rules follow the finos contract: base-10 ASCII digits, no leading zeros, unsigned 32-bit range. Python bool is a subclass of int, so the reader rejects True and False explicitly. Duplicate root members are detected with an object_pairs_hook, because json.loads otherwise keeps the last one silently.

This diverges on purpose. morphir-elm accepts only an integer, so it would reject "3.0.0"; the finos contract rejects "3" with invalid_format_version_syntax. The project accepts both so that migration work can read files written by older and newer tools. The divergence is stated in the package documentation.

Writers follow the finos contract: formatVersion first, integer N for N.0.0, exact string otherwise. A v3 writer therefore emits 3, which morphir-elm can read.

The support table is [3.0.0,3.1.0),[4.0.0,4.1.0). It is narrower than the finos reference table because this change does not implement IR 3.1.0; a "3.1.0" file fails with unsupported_format_version_minor, as decision 0018 expects of a 3.0.0 reader. Integers 1 and 2 are recognized and fail with unsupported_format_version_major. Each version-specific entry point applies its own family table, so the v3 decoder refuses 4.0.0 with unsupported_format_version_major.

Rejected: elm's integer-only reader (it blocks reading files from contract-conforming writers) and a fully strict finos reader (it blocks "3", which some tools write).

read_format_version(3)        # FormatVersion(3, 0, 0)
read_format_version("3")      # FormatVersion(3, 0, 0), divergence from the finos contract
read_format_version("3.0.0")  # FormatVersion(3, 0, 0), divergence from morphir-elm
read_format_version(True)     # invalid_format_version_type
read_format_version("3.1.0")  # unsupported_format_version_minor under this change's table

ELM-1. morphir-elm is normative for v3 content

The v3 model and JSON shapes follow morphir-elm at the pinned commit. The finos/morphir v3 schema (website/static/schemas/morphir-ir-v3.json, documented in docs/spec/ir/schemas/v3/) was derived from elm. Where it disagrees with elm about 3.0.0 content, elm wins. Example: the finos schema now admits a Specs distribution and string versions for 3.1.0, but elm format 3 has only Library. morphir-moonbit records the same rule. The only intended departure from elm is FV-1, which concerns the version field and not content.

Port checklist, in dependency order; each Python codec mirrors one elm module:

  • src/Morphir/Codec.elm (encodeUnit, decodeUnit)
  • src/Morphir/IR/Name/Codec.elm, Path/Codec.elm, QName/Codec.elm, FQName/Codec.elm
  • src/Morphir/IR/AccessControlled/Codec.elm, Documented/Codec.elm, Literal/Codec.elm
  • src/Morphir/IR/Type/Codec.elm (types, fields, specifications including DerivedTypeSpecification, definitions)
  • src/Morphir/IR/Value/Codec.elm (values, patterns, specifications, definitions)
  • src/Morphir/IR/Module/Codec.elm, Package/Codec.elm, Distribution/Codec.elm (Library only)
  • src/Morphir/IR/FormatVersion/Codec.elm (envelope; version reading replaced by FV-1)

As in elm, node codecs take attribute codecs as parameters. The distribution codec fixes type attributes to unit and value attributes to a v3 type. Generic node codecs also let callers read untyped node fragments, such as the kit's ["Literal", {}, ["WholeNumberLiteral", 42]] (finos/morphir spec/ir/mck/versions.feature, case versions-0001), without weakening the Library contract.

The CLI-only Distribution.Component codec and CodecV1 modules are not ported.

PKG-1. Versioned packages and import identity

Format-3 types and codecs live in morphir.ir.v3, with modules name, path, qname, fqname, access_controlled, documented, literal, type, value, module, package, distribution, and codec. The v3 classes are distinct from the v4 classes, so a type checker catches cross-version mixing. Migrations convert names and paths explicitly.

The current modules move to morphir.ir.v4: access_controlled, decorations, distribution, document, documented, fqname, json, literal, meta, module, name, package, path, qname, ref, type_constraints, type_def, type_spec, type, and value, plus the new draft codec. Each old path (for example morphir.ir.name, which tests import today) becomes a shim that re-exports from morphir.ir.v4, and morphir.ir keeps its __all__. A test asserts morphir.ir.Name is morphir.ir.v4.Name.

from morphir.ir import v3, v4
from morphir.ir.format_version import read_format_version
from morphir.ir.migrate import v3_to_v4, v4_to_v3
import morphir.ir as ir  # still v4; ir.Name is v4.Name

V4-1. Draft v4 JSON codec

Review blocker B1 was that v4 cannot be read at all, so a v4 convert command had nothing to call. This change adds morphir.ir.v4.codec with encode_versioned_distribution and decode_versioned_distribution.

Envelope (B2): the codec uses the finos v4 JSON profile envelope, which is the part of v4 with a settled contract. formatVersion comes first and follows FV-1. The distribution is an object wrapped by its kind, for example {"Library": {"packageName", "dependencies", "def"}}. Rejected: a Python-only v4 envelope, and a formatVersion: 4 stamp on the format-3 tagged-array shape. The finos stabilization note records that a BDD fixture made the second mistake.

Node spellings follow the canonical forms that the finos schema and kit cases carry at the pinned commit, with the decisions 0004–0014 applied. The stabilization note lists live contradictions, including value-node member names, attributes on value nodes, and Rust's attrs against the schema's attributes. Where the kit has no active case, the codec uses the schema spelling and records the choice in a module-level table so a later re-sync is mechanical. The reader accepts only spellings it recognizes and fails on anything else with a located diagnostic; it does not guess.

Python model gaps against upstream v4 are handled explicitly, not by reshaping the model in this change:

  • Native and External are value nodes in Python, but decision 0008 makes them definition bodies. Encoding them fails with a structured error naming the construct. Realignment is follow-up work.
  • Upstream v4 has Union types, IncompleteTypeDefinition, and annotations, which the Python model lacks. The decoder fails on them with unknown_node or unknown_member.
  • Upstream v4 Records spell fields as an object keyed by name (decision 0004). The Python model keeps an ordered list, so duplicate field names fail encoding with duplicate_member.
  • Decorations files (decorations.py) are not part of the distribution; decision 0014 keeps layered decorations out of v4.0.0. They are outside the codec and outside migration.

Every v4 doc page, docstring, and CLI report that touches v4 says "draft" and names the pinned finos/morphir commit.

VER-1. Package release version

Neither format 3 nor upstream v4 JSON has a package release version (decision 0017 puts versions in distribution bindings), but Python PackageInfo.version is a required str. The field becomes str | None = None.

  • Upgrade: v3_to_v4(dist, *, package_version: str | None = None) and the CLI flag --package-version. Without either, the version is absent. Nothing is invented.
  • Downgrade: the version is dropped and the warning package_version_dropped is returned. This is the one explicit exception to "no dropping of IR content", and it is allowed because the version is packaging metadata, not IR semantics.
  • The v4 codec does not write the version, because the profile has no member for it, and it decodes it as absent. This loss is documented.

MIG-1. Migrations live in morphir.ir.migrate

Pure functions v3_to_v4 and v4_to_v3 return Ok(value, warnings) or Err(diagnostics). Each diagnostic is a frozen dataclass with code, construct, location (a tuple path such as ("modules", "rentals", "values", "request", "body")), and message. A reverse migration collects every failure it finds in one pass, so users fix all problems at once. The CLI and library share these functions.

v4_to_v3 takes drop_source_locations: bool = False. This is the only opt-in loss. Constraints, extensions, and type-attribute sources are never dropped, because they can change meaning or carry data a consumer depends on.

CLI-1. morphir-tools interchange commands with Typer

morphir-tools is a stub today. The CLI uses Typer with a minimum version pinned on morphir-tools only; core morphir stays dependency-free. The console script is morphir-tools, with an ir command group:

morphir-tools ir inspect morphir-ir.json
morphir-tools ir convert morphir-ir.json --to v4 -o out.json [--package-version 1.2.0]
morphir-tools ir convert v4.json --to v3 -o out.json [--drop-source-locations]

inspect reads the version, decodes the file with the matching codec, and prints the normalized version, distribution kind, and package name; for v4 it also prints the draft notice. There is no separate load command, because loading is a library operation. convert writes to a temporary file in the target directory and renames it only on success, so a failed convert leaves no output file. Diagnostics go to stderr as code at location: message. Exit codes: 0 for success, including success with warnings; 1 for a diagnostic failure; 2 for a usage error, which is Typer's default.

The CLI does not mirror elm's version acceptance. Elm reads format 1; this change rejects 1, 2, and 3.1.x with the FV-1 diagnostics and says that they are follow-up work.

TST-1. Golden fixtures from real format-3 output

Fixtures must be format 3 written by morphir-elm or published by finos/morphir as v3 examples. Do not use the rentals example, which is format 2. Candidates:

  • morphir-elm tests-integration/cli/test-ir-files/*-ir.json (base, listType, multilevelModules, simpleTypeTree, simpleValueTree, tupleType; 99 B to 11 KB)
  • morphir-elm tests-integration/reference-model/morphir-ir.json for broad coverage
  • finos/morphir website/static/ir/examples/v3/greeting-example.json and rule-set-example.json

Copy them under tests/fixtures/ir/v3/ with a PROVENANCE.md that records the source repository, commit, path, and Apache-2.0 attribution. Tests assert decode→encode semantic equality, the v3→v4→v3 round trip, and v4 encode→decode for the migrated result. Hand-built small fixtures cover the draft v4 codec. morphir-elm is never a runtime or test-time dependency.

Upstream is still settling downgrade rules under finos bead morphir-diwy, and kit case versions-0002 (writing a Hole to v3) is still pending. The migration codes may therefore be renamed upstream. Migration plan

Land in this order: the format-version reader; the v3 model and codecs; the v4 relocation with shims and the optional package version; the draft v4 codec; migrations; the Typer CLI; fixtures and docs. Publish as a minor version while morphir is 0.x. Rollback is a revert of the PR series. Consumers do not need to rewrite IR on disk until they run convert.

Open questions

  • Should reverse migration map documentation that is None to "" behind an opt-in flag, as it does for source locations? This design follows moonbit and fails. Revisit when morphir-diwy publishes rules.
  • Should the reader also accept "N.minor" two-component strings? Not accepted now; add them only if real files need them.
  • When the kit gains a write-refusal role (versions-0002), should this package add a kit adapter? That is out of scope here.
  • Adopting IR 3.1.0 (v3 Specs, which would let v4 Specs downgrade) is tracked by finos/morphir-python#28.
