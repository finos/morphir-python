Context and evidence

See the proposal for motivation. The compiler and extension already exist. This design adds a public guide around their present contracts, with executable evidence for the instructions readers follow.

Goals and boundaries

Readers should install the right package, complete a small model round trip, use the IR/SDK library directly, and understand which host can run the extension. A contributor should preview the same site that CI checks and publishes. The contracts are in docs/site, docs/examples and docs/cli-integration.

The initial site uses one documentation tree with explicit release and development labels. It does not introduce an evaluator, a browser Python runtime, a benchmark claim about Rust performance, or a new extension adapter. Full historical version trees can follow when releases need them. The user selected current-support documentation; the MoonBit Extism proposal is separate and does not gate this site.

Decisions

SITE-1. Consume the published Telescope CLI

Start with Telescope 0.2.1. Pin the release archive and expected SHA-256 in repository-owned setup metadata for Linux x64 CI and macOS arm64 local use. Verify the binary version after installation. These targets have published qualification; document other platforms as unqualified. Telescope is build tooling, outside the Python runtime dependency graph. A stock binary requires no MoonBit compiler or neighboring checkout.

Use site/site.json, site/pages/ for the landing page, existing docs/ for guides and site/assets/ for repository assets. Explicit discovery/exclusions must keep templates, planning documents, OpenSpec changes and generated output out of navigation and search. Proposed mise tasks are site:setup, site:build, site:check, site:serve and docs:test. Setup should install only the tools each command needs.

Copying MoonBit's renderer would duplicate work now owned by Telescope; a separate Python documentation framework would split that shared foundation.

SITE-2. Reuse the Morphir MoonBit visual design

Use the blue/orange palette and responsive hero, code window, pipeline and feature cards from morphir-moonbit bd3adc52, adapting only the Python content and guide links. Keep the attributed CSS in site/theme/morphir.css and bridge Telescope shell variables to the same palette. The hero model is the checked examples/model/acme/models.py source; browser checks compare the displayed text and exercise both themes, viewports and deployment bases.

Telescope 0.2.1 has no consumer stylesheet hook and rejects a static assets/site.css collision. Append the consumer theme to stock generated CSS in a private build directory, run Telescope checks on those final bytes, then atomically promote the checked tree. A broken CSS reference must leave the previous publication unchanged. Report this reusable gap upstream and retain the published renderer rather than fork it. This workaround changes presentation, not the renderer or browser controls.

DOCS-2. Treat runnable snippets as maintained examples

Store canonical Python sources, CLI argument arrays, fixtures and expected results under examples/. Give runnable snippets stable example identifiers and source-region references. A small Python docs utility synchronizes marked fenced regions in committed Markdown and offers a check-only mode that fails on drift. This works with the stock Telescope CLI. Retain source-file links and downloadable examples. Do not copy a tutorial into multiple untracked code blocks.

Extend the existing docs test coverage to execute named API examples in isolated interpreters and run mypy/pyright, checking typed results, artifacts and diagnostics. Run CLI recipes in temporary directories against installed distributions, assert semantic round trips, and cover invalid source and nonempty output directories. Test snippets without executing submitted compiler input as part of compilation. Generated model behavior can be checked in a separate verification process, as existing compiler tests do.

Record example prerequisites in a small machine-readable manifest. Released quickstarts use an exact qualified package set installed outside the checkout; development examples use the candidate wheels already produced by CI and visibly say they require a source build. The site's main-branch freshness must not imply that an unreleased compact-v4 writer or migration is available in a released wheel. A single tree can carry both labels without a version-assembly pipeline.

Checks and publication

CI-1. Select docs work and promote one checked artifact

Add docs ownership to the existing CI selector. Keep specific site/example/workflow rules ahead of broad docs, scripts and workflow rules. Published prose/configuration selects static build/check/browser coverage. Example or referenced API/CLI changes also select the relevant installed-package tests, using compatible existing wheel artifacts. Host recipe/pin changes select host qualification. Unknown paths and full runs remain conservative, and selected jobs that fail, cancel, disappear or skip unexpectedly must fail the aggregate.

Factor reusable site build/check work so the main CI and deployment caller use one definition. Keep deployment in a separate trusted-main publication workflow, with pages: write and id-token: write only on the deploy job and the github-pages environment. PR validation has no deployment credentials. The CI workflow is also reused by package releases, whose callers grant no Pages permission. A separate workflow_run publisher therefore verifies the producer repository, event, main branch, workflow path and successful conclusion before downloading an artifact, then checks out its exact SHA. PR/fork/failed/unrelated producers are refused. A manual run ID provides rollback through the same checks. This avoids requesting publication permissions through package-release callers. Re-run required examples for the main candidate or verify the documented relevant-input equivalence contract; a cache hit alone is insufficient.

Initial checks run on Linux x64; validate local installation on macOS arm64. Broader package-platform coverage stays with existing package qualification. No new nightly schedule is needed. Measure representative run duration and artifact reuse during implementation; this proposal promises no unmeasured speedup.

Migration and rollback

Deliver the implementation in one PR if practical, with task groups carrying their own tests and docs. Preserve existing guide paths and enhance their content rather than delete the only instructions before the site is live. Add the site skeleton, checked examples and host guidance, then integrate the selector and publication job. Run the pinned consumer installation, project-base checks and browser smoke on the complete candidate.

After review and authorized merge, deploy the verified main artifact. If repository settings block it, provide the checked artifact and exact setting request. Roll back a bad publication by redeploying a retained previously verified site artifact or reverting the content change and validating that revision. Keep package/extension releases independent of a site rollback. Archive this OpenSpec change and close task beads only after the agreed implementation evidence exists.
