Context

See proposal.md for the motivation. PR #32 landed format 3.0.0 beside draft IR v4. The parts this change touches are:

ModuleState before this change
morphir.ir.format_versionV3_INTERVAL is [3.0.0,3.1.0); a 3.1.0 document fails with unsupported_format_version_minor and a pointer to issue #28.
morphir.ir.v3.distributionDistribution = Library.
morphir.ir.v3.codecdecode_distribution refuses every tag but Library; encode_versioned_distribution always writes 3.
morphir.ir.migratev3_to_v4 takes a Library; v4_to_v3 refuses Specs and Application with unsupported_v4_downgrade.
morphir_tools.cliir inspect and ir convert assume a v3 file holds a Library.

The v4 model and codec (morphir.ir.v4) are being realigned in parallel under morphir-ukvn.8.14. This change reads them but does not edit them, and keeps its edits to migrate.py on the Specs path.

Goals and non-goals

Goals: read every 3.0.x and 3.1.x single-file JSON document; read and write a v3 Specs; migrate Specs both ways; keep every 3.0.0 output byte-identical to before.

Non-goals:

  • v3 JSON and YAML document trees (see SCOPE-1; follow-up morphir-ukvn.8.17).
  • Any change to the v4 model or codec.
  • Formats 1 and 2 (morphir-ukvn.8.12).

Decisions

FV-1. Raise the table; keep one reader

V3_INTERVAL becomes [3.0.0,3.2.0), so SUPPORT_TABLE and V3_TABLE follow. A new constant V3_1 = FormatVersion(3, 1, 0) names the release that introduced Specs, so no module compares raw tuples. The human description of a table lists each minor family it covers (3.0.x, 3.1.x and draft 4.0.x), because the old "3.0.x" label would now be wrong. The issue #28 pointer in the minor diagnostic goes away; a 3.2.0 refusal names the table instead.

Alternative: a separate reader for 3.1. Rejected: the format-version contract has one reader per table, and the patch promise (decision 0016) says a ceiling on a minor boundary is all that changes.

V3-1. Specs is a second frozen dataclass

@dataclass(frozen=True)
class Specs:
    package_name: Path
    specification: package.Specification[None]
    dependencies: dict[Path, package.Specification[None]] = field(default_factory=dict)

type Distribution = Library | Specs

Field names follow Library and the v4 SpecsDistribution, so migration code reads the same in both directions. There is no version field: the model holds content, and the writer derives the version from it (V3-4). This mirrors Rust DistributionBody::Specs, minus Rust's stored major.

V3-2. The version check runs before the body decodes

decode_versioned_distribution reads the root with V3_TABLE, then reads the distribution tag. If the tag is Specs and the declared release is below V3_1, it raises specs_before_3_1 at formatVersion, before it decodes the body. Rust decodes first and checks after; the kit pins only the code, not the order. Checking first means a Specs mislabelled as 3 reports the root cause, not a body error. The check uses the normalized release, so the permissive spellings 3, "3" and "3.0.1" are all refused.

The code lives in morphir.ir.diagnostics as SPECS_BEFORE_3_1 = "specs_before_3_1", the upstream spelling.

V3-3. A Specs distribution's own modules are read strictly

The elm-faithful module-specification decoder ignores unknown members. Under it, a module definition ({"access": ..., "value": ...}) would fail only on a missing types, and a module carrying extra members would read silently. For a Specs distribution's own modules, the decoder first refuses any member other than types, values and doc with unknown_member at that member. Dependencies keep the existing reading, as in Rust (SpecsModuleEntry versus ModuleSpecEntry).

Difference from Rust: Rust's strict reader defaults a missing types or values to empty. This package keeps them required (missing_member), as its 3.0.0 decoder does for every module specification. Every known writer emits both, so no real document is affected.

V3-4. Writers emit the lowest version that fits

encode_versioned_distribution picks the version from the content: V3 (written 3) for a Library, V3_1 (written "3.1.0") for a Specs. The spelling comes from the existing write_format_version. A Library read at "3.1.0" is therefore written as 3. This is decision 0018's rule, and it keeps every Library readable by morphir-elm.

V3-5. finos/morphir is normative for 3.1.0 additions

morphir-elm stays normative for 3.0.0 content, but it has no Specs. For what 3.1.0 adds, the finos/morphir v3 spec and kit win, and morphir-rust cd9f7fb is the reference implementation. The unknown-tag diagnostic now names both kinds.

MIG-1. Typed overloads; specifications reuse the existing mappings

v3_to_v4 and v4_to_v3 keep their names and gain @overload signatures, so a caller that passes a Library still gets a Library type back:

@overload
def v3_to_v4(dist: dist3.Library, *, package_version: str | None = None) -> Ok[dist4.LibraryDistribution]: ...
@overload
def v3_to_v4(dist: dist3.Specs, *, package_version: str | None = None) -> Ok[dist4.SpecsDistribution]: ...
@overload
def v3_to_v4(dist: dist3.Distribution, *, package_version: str | None = None) -> Ok[dist4.LibraryDistribution | dist4.SpecsDistribution]: ...

A v3 Specs maps its package specification with _package_spec_up, the function that already maps dependencies. A v4 Specs maps with _Downgrade.package_spec, so it collects the same diagnostics (names, attributes, documentation) and warns package_version_dropped the same way. An Application is still refused with unsupported_v4_downgrade; decision 0018 says it has no v3 form. The Library path is untouched.

Alternative: new functions specs_v3_to_v4 and specs_v4_to_v3. Rejected: the CLI would need its own dispatch on kind, and the existing Specs refusal in v4_to_v3 would remain a trap.

CLI-1. The CLI dispatches on the decoded kind

ir inspect reports kind: Specs for a v3 Specs and the version as read (format: 3.1.0). ir convert passes the decoded v3 distribution to v3_to_v4 or the decoded v4 distribution to v4_to_v3, and writes with the codec's writer, so the lowest-version rule applies to --to v3 too. The help text names 3.0.x and 3.1.x.

SCOPE-1. v3 document trees are out of scope

Decision 0018 also adds v3 JSON and YAML document trees, which reuse the v4 tree layout (logical paths, stem escaping, path budget, fileNames, manifest version rules). morphir-python has no document tree reader or writer for v4 either, so a v3 tree would mean building the whole layout first. That is a separate capability with its own kit cases (document-tree-0010 to 0017). This change leaves it out, and the follow-up bead morphir-ukvn.8.17 tracks it. Without trees, the single-file rules are complete: a Specs or a Library at any supported 3.x release reads, and every write is single-file.

TST-1. Fixtures from the kit and the reference tests

Two small fixtures go into tests/fixtures/ir/v3/, recorded in PROVENANCE.md:

  • mck-distributions-0011-specs.json: the canonical JSON of kit case distributions-0011 (finos/morphir efa36060, spec/ir/mck/distributions.feature).
  • rust-classic-specs-transport.json: the SPECS document of morphir-rust cd9f7fb, crates/morphir-common/tests/classic_specs_transport.rs, which adds a dependency.

Both are inline strings upstream, so they are copied verbatim as the file content rather than byte-for-byte from a file. Unit tests round-trip them, compare the output to the kit's canonical JSON, and run them through the migrations; BDD scenarios run them through the CLI.

Risks and trade-offs

RiskMitigation
Callers that typed decode_versioned_distribution as returning Library now get a union.Breaking change named in the proposal and README. The migration overloads keep Library callers precise.
A Specs this package writes is refused by morphir-elm and other readers still on [3.0.0,3.1.0).Intended by decision 0018: only new content carries the new version, and a Library still writes 3.
Strictness differs from Rust when a Specs module omits types or values (V3-3).No known writer omits them; the difference is stated here and in the README.
The v4 model changes in parallel (morphir-ukvn.8.14) and could conflict with migrate.py.Edits stay on the Specs branch of the two public functions; no v4 file is edited.

Migration plan

No data migration. Every 3.0.0 file reads and writes as before. Callers that matched on the v3 decoder result add a Specs case. Rollback is a revert of the change; no stored state depends on it.

Open questions

  • finos/morphir-rust#262 tracks whether a v3 tree reader should answer the minor diagnostic for a later 3.x manifest. It matters only when SCOPE-1's follow-up implements trees.
