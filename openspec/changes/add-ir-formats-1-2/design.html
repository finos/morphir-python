Context

See proposal.md for the motivation. Today morphir.ir.format_version normalizes the integers 1 and 2 to releases 1.0.0 and 2.0.0 only so that check_supported can refuse them with unsupported_format_version_major ("formats 1 and 2 are follow-up work"). The support table is [3.0.0,3.2.0),[4.0.0,4.1.0) since bead morphir-ukvn.8.13 (IR 3.1.0, PR #34) merged; this change does not touch the table. That change also made the v3 distribution Library | Specs; the legacy formats only ever produce a Library, because Specs needs format 3.1.0.

The finos/morphir format-version contract (kb/bundles/morphir/morphir-ir/format-version-support.md) says the release grammar starts at major 3. A support table therefore cannot hold format 1 or 2.

morphir-elm at bc99af69 is the source. Its FormatVersion/Codec.elm reads format 3 with Distribution.Codec, format 1 with Distribution.CodecV1, and refuses everything else, format 2 included, with "Please regenerate it!".

What formats 1 and 2 are

From the morphir-elm history:

CommitDateEffect
8e0e729d2021-10-08Copies the codecs to */CodecV1.elm, sets currentFormatVersion = 2, and decodes format 1 with CodecV1.
e742a6202021-10-08Format 2 shapes: TitleCase distribution, access, type and literal tags; {"access", "value"}; {"doc", "value"}; [path, module] package entries; {"name", "tpe"} fields.
02aa36af2023-05-18Format 3: value and pattern tags become TitleCase. The old value codec is kept as Value/CodecV2.elm with Distribution/CodecV2.elm.
7cb7b3002023-05-18Removes the V2 codecs. Format 2 is refused from then on.

git diff 02aa36af^ bc99af69 over src/Morphir/IR/*/Codec.elm shows that only the value codec changed shape between format 2 and today's format 3 (the Decoration, Component and Source codecs also changed, and the Library distribution uses none of them). So format 2 is format 3.0.0 with snake_case value and pattern tags.

The removed Distribution/CodecV2.elm called Package.Codec, which by then used the TitleCase value codec, so elm's own format-2 reader could not read real format-2 values. This design ports the format, not that reader.

Goals and non-goals

Goals: read formats 1 and 2 exactly as morphir-elm wrote them, into the existing v3 model; let the CLI upgrade them; keep the support table, the diagnostic codes, and the format 3.0.0 codec as they are.

Non-goals: writing formats 1 or 2; files with no formatVersion (still missing_format_version); the string spellings "1" and "2", which no tool wrote; a separate Python model for the legacy formats.

Decisions

FV-2. A legacy path beside the support table

format_version gains a LegacyFormat enum (V1, V2) and two readers:

def recognize_legacy_format(value: object) -> LegacyFormat | None: ...

def read_document_with_legacy(
    document: str | object, table: SupportTable = SUPPORT_TABLE
) -> tuple[FormatVersion | LegacyFormat, dict[str, object]]: ...

def read_legacy_document(document: str | object, accepted: LegacyFormat) -> dict[str, object]: ...

Only a JSON integer 1 or 2 (not a boolean) is legacy. Every other value goes through read_format_version unchanged, so it fails with the same codes. read_format_version and read_document keep refusing 1 and 2 with unsupported_format_version_major; only the message changes, from "follow-up work" to the names of the legacy readers. read_legacy_document refuses any version but the one it is asked for with unsupported_format_version_major. No new diagnostic code is needed.

Alternatives. Adding [1.0.0,1.1.0) and [2.0.0,2.1.0) to the table breaks the finos grammar and changes the table spelling that tools and reports compare. A boolean flag on read_document would put the legacy rule inside the code path that bead morphir-ukvn.8.13 edits. The new functions sit at the end of the module; the only shared edits are a message string, a refactor of read_document into a private root reader, and a guard in write_format_version.

FV-3. Writers never emit 1 or 2

write_format_version raises ValueError for a major below 3. A FormatVersion(1, 0, 0) can still come out of recognize_format_version, so the guard keeps a mistake from writing it. The legacy modules have no encoders.

CDC-1. Legacy decoders in their own modules, into the v3 model

As in elm, the legacy decoders produce the same model as format 3.0.0, so decoding is the upgrade and morphir.ir.migrate needs no new function. The modules are:

ModulePortsPublic decoders
morphir.ir.v3.codec_v1morphir-elm */CodecV1.elm at bc99af69 (decoders)literal, type, type spec and definition, access control, documented, pattern, value, value spec and definition, module, package, distribution, versioned distribution
morphir.ir.v3.codec_v2Value/CodecV2.elm at 02aa36af, with the format 3.0.0 codec for the restpattern, value, value definition, module and package definition, distribution, versioned distribution
morphir.ir.v3._legacy_value (private)The snake_case value and pattern decoders that formats 1 and 2 shareBuilt from a literal decoder and a type decoder, because literals and types differ between the two formats

The format 3.0.0 codec is not edited: it still refuses 1 and 2, and bead morphir-ukvn.8.13 can change it without conflicts. The legacy modules import its primitive helpers (_tag, _field, and so on) rather than copy them.

Alternatives. A tag-renaming JSON rewrite cannot work, because "variable", "reference", "tuple", "record" and "unit" are both type and value tags and the shapes around them differ. Parameterizing the 3.0.0 codec by spelling would branch inside it.

CDC-2. Faithful to the elm decoders, including their quirks

  • Documented (format 1) is elm's Decode.oneOf: try [doc, x], then the bare x. When both fail, the DiagnosticError holds the diagnostics of both, as elm's oneOf error lists both.
  • Derived types: elm CodecV1.encodeSpecification writes "DerivedTypeSpecification" but decodeSpecification reads only "derived_type_specification". Derived types reached CodecV1 in 2022, after format 1 stopped being written, so no real file has them; the port follows the decoder.
  • Format 1 module specifications and definitions decode with doc = None and ignore a doc member (Decode.succeed Nothing). Format 2 reads the optional doc, as format 3.0.0 does.
  • Literal payloads are checked by the format 3.0.0 literal decoder after the tag is renamed, so the rules for characters, integers and decimals are the same.

CDC-3. morphir-elm wins over the finos v2 schema docs

finos/morphir docs/spec/ir/schemas/v2/whats-new.md says format 2 literals stay snake_case and names an integer literal whole_number_literal. morphir-elm wrote "StringLiteral" in format 2 (see the rentals fixture) and "int_literal" in format 1. As for format 3, morphir-elm is normative.

CLI-2. Dispatch in the CLI

ir inspect and ir convert read the root with read_document_with_legacy and choose codec_v1, codec_v2, the 3.0.0 codec or the v4 codec. Inspect prints format: 1 (legacy) and a note that ir convert upgrades the file. Convert writes format 3.0.0 or, through v3_to_v4, draft v4. The Target enum stays v3 and v4: there is no way to ask for format 1 or 2.

TST-2. Real fixtures, one model in two formats

morphir-elm tests-integration/cli/test-data/rentals/ has the same example written as format 1 (expected-morphir-ir-v1.json) and as format 2 (expected-morphir-ir.json). Both are copied byte for byte to tests/fixtures/ir/legacy/. Decoding both must give the same Library, which checks the two decoders against each other. Hand-written JSON covers every tag that the small fixtures do not use, with the spellings taken from the elm source.

Risks and trade-offs

RiskMitigation
Format-1 files written before later CodecV1 edits (value documentation in 2022, decimals) may differ from what the elm decoder reads today.The port follows today's elm decoder, which is what morphir-elm users get. Documented entries accept the bare value, which covers files written before value documentation.
The fixtures are small and use few tags.Per-tag unit tests with hand-written JSON for every type, value, pattern, literal and wrapper tag.
Importing private helpers from codec.py couples the modules.The helpers are stable JSON-shape checks. Moving them to a shared module would edit codec.py, which bead morphir-ukvn.8.13 edits in parallel; that can be a later refactor.
Rebase conflicts with IR 3.1.0 in format_version.py, the CLI, and the specs.The support table and the 3.1 message are not touched; the legacy code is appended in its own section. This branch was rebased on PR #34 and its spec deltas rewritten against the merged specs.

Migration plan

No data migration. Users who got unsupported_format_version_major for a format-1 or format-2 file can now run morphir-tools ir convert old.json --to v3 -o new.json. Rollback is a revert: no stored data or public name is removed.
